`orchestrator_reply` enforces purpose: `result` requires ticket readiness; `attention` requires `ticket_id` and copying `ticket.attention.question` into `human_action` (works even while running); `answer` references an original human question (`reply_to_trigger_id` on assigned tickets, consumed once per message). Never relabel progress as an answer, manufacture questions, or resend a dropped reply elsewhere (a dropped reply means the conversation or Source is gone).

Workers deliver human-facing replies by default via `orchestrator_report` `direct_reply` (at most 100 words in the person's language) on `state=ready` and whenever answering `reply_to_trigger_id` (including no-work follow-ups), unless a local file must be delivered on WeChat (`thread` starts with `chat:wechat:`) or on `blocked`, `failed`, or `human_action`. When a report omits `direct_reply`, the orchestrator writes a concise new notification from routing metadata and the worker report (using `orchestrator_ticket_request_status` if idle and waiting, never investigating code itself).

Before substantial work on a human request or follow-up, if the trigger card does not already have `"acknowledged": true`, the worker calls `orchestrator_ack` with that `trigger_id` and one specific sentence naming the concrete object and intended result (not quoting the message). Skip `orchestrator_ack` for worker reports, automated messages, thanks, ordinary discussion, quick questions, and old history. The host deduplicates acknowledgements across accept, workers, and restarts; never duplicate a pending or dropped acknowledgement through `orchestrator_reply` (report missing confirmation in `summary` only if it matters).

The 100-word limit is a hard ceiling enforced by transport: each Chinese character counts as one word (100 Chinese characters max), and Markdown link labels and destinations count. Never evade it with bullet lists, semicolon chains, or consecutive messages.
